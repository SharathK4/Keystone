4. CREATIVE DIRECTION (used for 1e and Phase 2; the frontend/README.md principles stay and this adds to them)
Goal: in 20 seconds, without reading, a viewer feels serious structural work was done on payments and wants to touch it. Every backend layer (honest evaluation, twin-world replay, inference, optimisation, execution) must be something you can see, touch or inspect, not a dashboard of metrics.
Anti-goals: no animated or force-directed network graph; no play, pause or scrub; no "simulation running" language; no autoplay montage; no glow, pulse, particles or decorative gradients; no stock or generated imagery; no KPI-card dashboard; no chatbot as the main interface; no user-facing words "engine", "simulator", "risk score" or "AI-powered".
Provenance: every figure carries one of four kinds, derived from the endpoint class and never typed by hand: Computed now (a user-triggered bounded analysis, with measured ms); Replayed offline (precomputed on a snapshot id, with scenario count and interval); Executed in PayPal sandbox (with the PayPal reference id); Inferred (with measured recovery quality).
Concept A, an engineer's survey of a building made of payments, in numbered plates. Vocabulary: merchant = stone, tier = course, dependency = bearing, recovery plan = shoring, money arriving = settlement. This is a metaphor, not claimed physics.
 Plate I The Structure: the hundred merchants as stones in courses by tier, keystones marked; a toggle shows the inferred dependencies (the existing chord diagram) with its measured recovery quality stamped.
 Plate II Pull a Stone: pick any stone; affected stones change state (hatch AND tone, never colour alone); a result panel with merchants affected, amount at stake (units labelled) and time to first constraint with its interval.
 Plate III The Cost of Waiting: a discrete rail selector (scenario parameters, not production timings); two curves, fixed plan and re-planned, with the gap shaded and annotated.
 Plate IV The Offer: the provider-neutral contract card; a "same week, twice" paired panel (no fix vs fix, same random draws); candidate ranking with the exact-optimum tick and the gap printed; deliberate approval; PayPal sandbox execution; a ruled ledger of events with reference ids; the failure path offering a re-plan.
 Plate V Proof: an inspection certificate from an offline, content-addressed artifact: the leakage cutoff diagram, audit checks as stamped lines, measured results with intervals, and a "What failed" block stating the honest weaknesses up front.
Pitch map: leakage barrier -> Plate V diagram and a margin note on Plate II; counterfactual replay with common random numbers -> Plate IV "same week, twice"; dependency inference -> Plate I toggle with recovery stamp; optimiser with exact reference -> Plate IV ranking; provenance hashes -> a seal component on every figure; execution layer -> Plate IV approval and ledger; value of speed -> Plate III; audit and tests -> Plate V; honest limits -> Plate V.
Live interactions, never video: (1) Pull a stone, as an explicit user-triggered POST to the existing bounded analysis only if it responds fast in the serving process without training code (measure it; otherwise precompute all 100 single-merchant failures offline and label them Replayed offline). (2) Set the rail: a discrete choice over precomputed replays, labelled. (3) Sign the offer: a two-step deliberate approval (keyboard path required), then a real sandbox execution, then the ledger updating on open or explicit refresh.
Visual system: paper and stone grain from SVG filters (the existing textured-tile family); the four existing colourways reused as inks; hairline rules, plate numbers, captions, dimension lines, marginalia for method notes; a serif display plus a monospace for figures, both SIL OFL; everything drawn by code; the landing carries no metrics.
Motion: nothing autonomous and nothing that loops. Motion only as a direct response to a user action: single-shot, 300 ms or less, honouring prefers-reduced-motion. No timeline playback anywhere.
Accessibility: a keyboard path for every interaction; state never by colour alone; AA contrast; aria-live announcements for results; a text summary per plate.
Data honesty: every rendered number traces to an API field; no hard-coded numbers in the frontend; fixtures only in tests; units always labelled.
Exceptions to the existing frontend principles, and only these: (E1) single-shot user-triggered transitions; (E2) user-triggered POST analysis; (E3) uncached execution and ledger reads refreshed only on open or explicit action; (E4) the stone wall replacing the hundred-dot grid, only if the human picks Concept A.
Execution UI states: recorded as plan / awaiting approval / executed in PayPal sandbox at demo scale with reference ids / failed with reason; derived from /execution/status and execution records, never inferred client-side. Units: analytic quantities in rupees and index units; executed quantities in sandbox currency at the declared demo scale; never mixed in one number.
